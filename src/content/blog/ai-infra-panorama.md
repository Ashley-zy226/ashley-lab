## 一、破题与边界：AI Infra 到底在研究什么？

大模型体系通常可以粗略分为三层分工：
- **应用层**：把模型接进业务场景（RAG、Agent、对话交互）。
- **算法层**：设计模型结构与训练范式，让模型更“聪明”。
- **AI Infra（人工智能基础设施）层**：在有限的硬件物理上限下，通过系统软件、算子、并行与调度创新，让大模型**训得动、推得快、撑得起更大规模与更长上下文**。

为什么 AI Infra 会成为近几年系统领域顶会（MLSys、OSDI、SOSP、ASPLOS 等）最火热的方向？核心矛盾非常朴素：**大模型参数量与上下文长度呈指数级膨胀，而单张芯片的算力、显存容量与显存带宽增长远远跟不上**。几乎所有 AI Infra 研究，都是在围绕这一物理矛盾做文章。

## 二、硬件底座与互联：所有上层优化的“物理天花板”

如果不了解底层硬件的物理约束，看上层论文里的 FlashAttention、低比特计算、PD 分离都会觉得像“黑魔法”。理解硬件底座，抓住三个最核心的概念就够了。

### 1. 异构芯片架构：为什么 AI 需要 GPU 与 NPU？

- **CPU** 像少数几位“全能教授”，擅长复杂逻辑判断和串行控制，但同时算不了太多简单乘法。
- **GPU** 像成千上万名“小学生”，单人逻辑简单，但极度擅长把大矩阵拆开、大规模并行地做乘加运算；现代 GPU 还专门内置了面向矩阵乘法的 **Tensor Core**。
- **专用 NPU / ASIC**（如 Google TPU、华为昇腾 NPU）更进一步，干脆砍掉更多通用控制电路，把芯片面积极致投入到矩阵与向量计算单元上。

这种从通用计算走向专用加速的**异构硬件趋势**，也直接催生了后文要讲的跨芯片编译器研究。

### 2. 存储层级：越靠近算力，越快、越小

数据要送到计算单元手里，必须穿过一条明显的“速度-容量金字塔”：

> **本地磁盘 SSD（TB 级，最慢） → 主机内存 DDR（百 GB~TB） → GPU 显存 HBM（数十 GB） → 片上 SRAM / 寄存器（MB 级，极快）**

这里卡着两堵著名的<strong>“显存墙”</strong>：
- **容量墙**：模型权重、训练状态或推理缓存太大，显存直接装不下（OOM）。
- **带宽墙**：现代芯片的算力飙升得比显存带宽快得多，很多时候计算核心并不是算得慢，而是在**空等数据从 HBM 慢吞吞地搬过来**。

### 3. Roofline 模型：读懂所有系统论文的第一把钥匙

如何一眼判断一个 AI 任务到底是“算力不够用”，还是“搬数据太慢”？系统领域最经典的工具就是 **Roofline 模型**——它不需要复杂推导，只需要建立一个核心直觉：

![硬件物理约束：存储层级与 Roofline 模型](/images/ai-infra-panorama/02_hardware_roofline.png)

- **访存受限（Memory-bound）**：落在左侧斜坡上。每搬运 1 字节数据只做很少的计算，算力核心大量空转（比如大模型逐字生成阶段的 Decode、逐元素激活算子）。**破局思路：减少 HBM 读写次数，尽量把数据留在极快的片上 SRAM 里反复复用。**
- **算力受限（Compute-bound）**：落在右侧平顶上。数据复用率够高，已经触碰到硬件峰值算力天花板（比如大 Batch 矩阵乘、长文本 Prefill）。**破局思路：采用更低比特计算（如 FP8）或更强算力芯片。**

> **初学者最容易踩的认知误区：显存占满 ≠ 算力吃满**\
> 看到显存占用 95%，并不代表 GPU 正在满负荷计算。如果任务落在 Roofline 左侧的访存受限区，显存即使塞满，计算单元依然可能处于“干等数据”的闲置状态。

此外，当单张卡无论容量还是算力都不够时，多卡之间需要通过<strong>机内高速互联（如 NVLink）</strong>和<strong>跨机高速网络（如 InfiniBand / RoCE）</strong>交换数据——跨卡网络带宽远低于卡内显存带宽，这就构成了第三堵墙：**通信墙**。

## 三、系统软件、编译器与算子：压榨单卡极限的核心战场

硬件提供了物理上限，但真正决定能不能把上限跑出来的，是紧贴硬件的**系统软件、编译器与算子层**。

最底层是**设备接入与异构软件底座**：操作系统驱动负责管硬件，**NVIDIA CUDA**（以及对标生态 AMD **ROCm**、华为昇腾 **CANN**）提供统一运行时，再借助容器设备映射让上层程序能安全调用加速卡。了解这层“地基”后，学术界真正重点攻关的是以下三大方向：

### 1. IO-Aware 算子设计：把数据留在片上算完

传统写算子往往只关心“数学计算量（FLOPs）少不少”，但 Roofline 模型告诉我们，很多时候真正耗时的是 **HBM 读写（IO）**。**IO-Aware（访存感知）算子设计**的核心思想，就是围绕存储层级重新编排计算顺序。

最具代表性的里程碑工作是 **FlashAttention**：
- 标准注意力机制会先算出一个巨大的中间注意力矩阵并写回慢速 HBM，做完 Softmax 再读回来，长文本下不仅爆显存，还被 HBM 带宽拖死。
- **FlashAttention 的直觉非常巧妙**：把输入矩阵切成小块（Tiling），一块块搬进速度极快的**片上 SRAM** 里直接算完局部结果并动态更新，**全程不把庞大的中间矩阵写回 HBM**。数学结果完全等价，速度却大幅提升、显存占用锐减。

### 2. AI 编译器与 DSL（Triton / MLIR）：告别纯手写 CUDA

过去想榨干 GPU 性能，必须靠专家用 **CUDA C++** 手写底层算子（Kernel），开发门槛极高。但如今新模型结构层出不穷，国产和异构芯片百花齐放，全靠人手写根本跟不上——于是<strong>编译器与领域专用语言（DSL）</strong>成了科研重镇：

- **Triton**：用接近 Python 的语法，以“数据块（Block）”为单位写算子，编译器自动帮你搞定繁琐的底层内存对齐与片上调度，大幅降低高性能算子研发门槛。
- **MLIR 与图编译（如 `torch.compile`）**：通过多层中间表示（IR），把高层神经网络自动做**算子融合**（把几个连续小算子合成一个，省去中间读写 HBM 的开销），并探索将同一份模型代码自动编译适配到 GPU、TPU、NPU 等多种异构芯片上。

> **一个小提醒**：初学者常把 **OpenAI Triton**（写 GPU 算子的编程语言与编译器）和 **NVIDIA Triton Inference Server**（模型部署服务框架）搞混，二者同名但处于完全不同的层级。

### 3. 低比特计算（Low-bit Computing）：突破算力与带宽的双重红利

把模型参数与计算精度从传统的 FP32 / BF16 压低到 **FP8、INT4** 甚至更低比特，为什么是系统与算法界共同追捧的热点？
- **在访存受限区**：数据体积直接砍半甚至砍到四分之一，显存容量压力与 HBM 搬运量同步骤降；
- **在算力受限区**：新一代 AI 芯片专门为 FP8 / FP4 设计了更高吞吐的矩阵指令，直接把 Roofline 的平顶往上抬高一截。

当然，比特越低越容易出现数值溢出和模型“变傻”，如何设计兼顾硬件友好与模型精度的量化格式与底层融合算子，是当前顶会非常活跃的交叉方向。

## 四、分布式训练框架：单卡装不下，如何千卡协同？

进入大模型训练阶段，显存里不仅要放模型权重，还要存前向激活值、梯度和优化器状态，单张卡远远装不下。借助 **PyTorch** 这一事实标准框架底座，分布式训练（如 Megatron-LM、DeepSpeed、TorchTitan）通过多维切分把任务拆到成百上千张卡上。

在认识前沿研究之前，先用一句话记住三种经典并行基石：
- **DP（数据并行）**：每卡吃不同的训练数据，算完同步梯度；**ZeRO / FSDP** 进一步把参数和状态分片到各卡，消除显存冗余。
- **TP（张量并行）**：把单层里的巨型权重矩阵切开分给多卡算，通信极频繁，通常限制在机内高速互联（NVLink）中。
- **PP（流水线并行）**：按网络层数切分，像工厂流水线一样卡间接力传激活值，适合跨机，但容易出现等待“气泡”。

而在当前 MLSys / OSDI / SOSP 科研视角下，更值得初学者重点关注的是以下**三大前沿主题**：

![分布式训练全景：多维并行切分与通信计算重叠](/images/ai-infra-panorama/03_distributed_training.png)

### 1. 新架构并行：MoE 与专家并行（EP）

现代前沿大模型（如 DeepSeek等）普遍采用 **MoE（混合专家）** 架构：模型总参数极大，但每个 Token 只稀疏激活其中少数几个“专家”网络，从而用更低计算量换取更强能力。

对应的并行方式叫 **专家并行（EP, Expert Parallelism）**：把不同专家分散放到不同 GPU 上，每个 Token 通过路由器经由 **All-to-All** 跨卡通信发往对应专家。这直接带来了学术界最头疼的两个系统难题：
- **动态负载不均衡**：如果大量 Token 恰好都涌向某几个“热门专家”，对应 GPU 就会卡死，全集群被迫干等；
- **跨节点通信瓶颈**：高频的 All-to-All 流量很容易打满网络带宽。

### 2. 超长上下文并行（CP）

当大模型的上下文窗口拉长到 128K 甚至百万级 Token 时，哪怕单条样本的前向激活值也能轻松撑爆单卡显存。<strong>上下文并行（CP, Context Parallelism）</strong>把一条超长序列按长度切分到多张卡上协同计算注意力——例如经典的 **Ring Attention**，让各卡排成一圈，一边计算局部注意力，一边像传接力棒一样环形交换历史 K/V 数据块。

### 3. 通信与计算重叠（Communication-Computation Overlap）

多卡分布式训练最怕“算的时候网络闲着，传数据的时候昂贵的 GPU 在发呆”。因此，几乎所有顶级分布式训练系统论文都在围绕一个核心思想做极致打磨：**把大块通信拆细，通过异步调度把通信时间完全“藏”进 GPU 计算的时间窗口里**，最大程度消除硬件空转气泡。

## 五、大模型推理与服务化：算法-系统协同的主战场

模型训练完成后进入**推理（Inference）**阶段：权重冻结、只做前向计算，看起来比训练简单，但实际上由于大模型的**自回归逐字生成**特性，推理反而成了当下论文产出最快、技术迭代最猛烈的领域。

### 1. 理解一切推理优化的钥匙：Prefill vs Decode

每当你发给大模型一段提问，推理内部都会拆成两个物理特性**截然相反**的阶段：
- **Prefill（预填充）**：把你输入的所有 Prompt 一次性并行算完，产出第一个字，并把计算过程中产生的中间状态缓存在显存里——这就是著名的 **KV Cache**（用空间换时间，避免后面每吐一个字都重算整段历史）。这一阶段计算密集，属于 **Compute-bound**。
- **Decode（逐字解码）**：此后每轮只生成 **1 个新 Token**，但为了算出这 1 个字，GPU 必须把庞大的模型权重和越来越长的历史 KV Cache 完整地从 HBM 搬进算力核心读一遍。算术强度极低，是典型的 **Memory-bound**。

随着对话越来越长、并发请求越来越多，KV Cache 的体积会迅速超过模型权重本身，成为推理的头号瓶颈。早期系统工作（如 **vLLM** 开创的 **PagedAttention** 分页管理减少显存碎片，以及 **Continuous Batching** 按迭代动态插队提升吞吐）奠定了现代推理引擎的基础。

### 2. 科研核心前沿：四大算法-系统协同方向

当纯工程手段逐渐逼近物理极限，学术界开始打破“算法只管改模型、系统只管做加速”的隔阂，走向**算法-系统协同设计（Algorithm-System Co-design）**：

![大模型推理的核心矛盾与算法-系统协同](/images/ai-infra-panorama/04_inference_codesign.png)

1. **MLA 等 KV 压缩架构**：与其在系统层费尽心思给庞大的 KV Cache 做分页和换出，不如直接从模型注意力结构下手——例如从 GQA 演进到 DeepSeek 提出的 **MLA（多头潜在注意力）**，通过低秩投影把 KV 压缩存进极小的潜空间里，从源头把显存容量与带宽占用打下来。
2. **投机解码（Speculative Decoding）**：既然 Decode 阶段“算力闲得发慌、带宽卡得死死的”，那就引入一个极轻量的草稿机制快速连猜好几个 Token，再让大模型用**一次前向计算并行验证**它们。猜对的直接采纳，既把一次访存的利用率拉高数倍，又能在数学上保证最终输出分布与原模型**完全无损一致**。
3. **动态稀疏（Dynamic Sparsity）**：面对十万、百万字的上下文，生成当前这一个字时，真正相关的历史信息往往只占极小一部分。动态稀疏方法在推理运行时实时筛选出关键的 KV 块参与注意力计算，直接跳过大量无关历史，大幅削减长文本的访存与计算开销。
4. **PD 分离与新型调度（Prefill-Decode Disaggregation）**：既然 Prefill 吃算力、Decode 吃带宽，把它们混在同一张卡上跑必然互相干扰（一个重型长输入 Prefill 会瞬间卡住所有正在流畅吐字的 Decode 请求）。**PD 分离**将两阶段解耦到不同的计算节点甚至不同的硬件配比上，Prefill 节点算完后通过高速网络将 KV Cache 交给 Decode 节点专心吐字，成为近年 OSDI / SOSP 最具代表性的推理架构演进之一。

在生态工具上，**vLLM**、**SGLang** 等开源推理引擎不仅是工业界的主流部署方案，也是学术界复现和验证上述系统创新的常用实验底座。

## 六、集群编排与可观测性：宏观了解即可

站在全景图最上层的，是把单机/多机资源组织起来跑任务的基础设施，以及贯穿全栈的观测体系。在科研导向的入门阶段，这一层**无需深究大厂复杂的线上运维细节，知道几个常见名词的角色分工即可**：

- **容器与集群调度**：**Docker** 用来打包统一的软件环境，避免“在我电脑上能跑、上集群就报错”；在多机多卡资源分配上，高校实验室和大规模离线训练集群普遍使用轻量直接的 **Slurm** 提交作业，而云原生环境与在线服务集群则常见 **Kubernetes + Ray** 负责多节点资源编排与任务分发。
- **观测与性能剖析（Profiling）**：在线系统常用 **Metrics（指标）、Logs（日志）、Trace（链路追踪）** 监控吞吐与延迟；而对于做 AI Infra 研究来说，最亲密的日常工具是底层的 **GPU Profiling 工具**（如 **PyTorch Profiler**、**NVIDIA Nsight Systems / Compute**）——它们能把 GPU 时间线摊开在你面前，让你清晰看到时间到底是被算子计算、HBM 访存还是跨卡通信吃掉了。

## 结语：用一条主线收束整张地图

回顾全文，看似庞杂的 AI Infra 技术栈，其实可以被一条极其清晰的逻辑主线串起来：

> **硬件物理上限（Roofline / 存储层级 / 通信墙）**\
> → <strong>算子与编译器（IO-Aware / Triton / MLIR / 低比特）</strong>逼近单卡极限\
> → <strong>分布式训练（3D 并行 / MoE EP / 长文本 CP / 通信计算重叠）</strong>突破单卡边界\
> → <strong>推理算法-系统协同（MLA / 投机解码 / 动态稀疏 / PD 分离）</strong>改写传统性能权衡

当你以后再打开一篇 MLSys、OSDI 或 SOSP 的新论文时，不妨先问自己两个问题：**它落在这张全景图的哪一层？它在挑战哪一堵物理墙？** 只要想明白这两点，你就已经真正跨进 AI Infra 的大门了。
